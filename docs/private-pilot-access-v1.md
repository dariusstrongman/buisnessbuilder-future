# Private pilot access v1

This narrow path admits one founder-approved, residential-cleaning Build My Business + Build & Run company at $0 Business Builder fees. It does not represent a Stripe payment, create a Stripe customer or subscription, waive third-party costs, or mark work Ready/Fully Set.

The authenticated founder submits `POST /api/v1/orders/{order_id}/pilot-access?company_id={company_id}` with `{ "code": "<submitted value>" }`. The company selector is only a routing hint. The customer API revalidates the server-created principal, active membership/organization/company scope, order owner, and granted Runtime founder approval. The only response body is `{ "result": "VALID" }` or `{ "result": "INVALID" }`; the configured or submitted value is never echoed. Existing company redemption is returned idempotently without re-reading the secret.

The application task role reads `business-builder/pilot-access` at request time via Secrets Manager and extracts only JSON key `promo_code`. The code is compared in process with `hmac.compare_digest`. No secret is cached, persisted, audited, logged, embedded in SQS or frontend bundles, or supplied through a `NEXT_PUBLIC_*` variable. An unavailable or malformed secret fails closed as `INVALID` for new redemption. The current ECS task role has a separate inline policy allowing only `secretsmanager:GetSecretValue` on this exact secret ARN; no wildcard Secrets Manager permission is needed. Do not modify or copy the secret value to configure the application.

Commercial persists one immutable `PilotRedemption` per tenant/company and safe invalid/unavailable attempt records in its existing append-versioned ledger. PostgreSQL serializes company redemption with a transaction-scoped advisory lock. Five failed validation attempts in 15 minutes block further attempts in that window. The $0 order has `access_source=PILOT_ACCESS`, status `fulfillment_pending`, zero-valued BUILD_BUSINESS and BUILD_AND_RUN items, and no checkout/payment/subscription refs. Both customer-owned and managed entitlements have `provenance=PILOT_ACCESS`. Order, redemption, entitlements, audit, and Runtime outbox events commit together. Stripe webhooks remain exclusively authoritative for paid orders; the pilot path never synthesizes a billing event. Existing Runtime, Company Brain, Founder Action evidence, Verification, budget, and tenant-isolation checks still apply.

The flagship BFF maps `/api/product/orders/{order_id}/pilot-access` to the customer API over the authenticated HttpOnly session boundary. It requires a same-origin mutation and forwards no caller-supplied tenant, role, or actor authority. The field appears only on an approved, uncharged new-business draft. Pending and invalid outcomes remain generic; on success the UI reloads persisted order, entitlements, and Build Room rather than scripting progress. The pilot value is cleared from the input after submission.

This branch alone is not a deployment or live acceptance proof.
